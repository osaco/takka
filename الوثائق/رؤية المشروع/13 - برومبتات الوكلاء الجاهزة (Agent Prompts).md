### W0-1 · قياس أداء Canvas على جهاز أندرويد ضعيف

```text
أنت وكيل بحث/قياس في مشروع «تكة» — تطبيق تعليمي ترفيهي عربي لأطفال غزة (الصفوف 1–6)،
أوفلاين أولاً، على أجهزة أندرويد ضعيفة (2GB RAM).

المهمة: W0-1 — قياس أداء Canvas 2.5D لتحديد إن كان العالم الحالي صالحاً للاستمرار.

الهدف:
معرفة ما إذا كان عالم الجزر 2.5D الحالي يعمل بـ 30fps على الأقل على جهاز 2GB،
قبل تثبيت قرار «الاستمرار بالـ Canvas أو الانتقال».

أسئلة البحث:
1. ما متوسط الإطارات (fps) لخريطة بعدد N عنصراً (50، 100، 200، 400)؟
2. أين الاختناق: الرسم؟ الظلال؟ النص؟ عدد طبقات canvas؟
3. أثر devicePixelRatio 1 مقابل 2 على fps والذاكرة؟
4. هل offscreenCanvas يحسّن الأداء على WebView أندرويد؟
5. أثر requestAnimationFrame عند انخفاض البطارية؟

الطريقة:
- قياس فعلي على جهاز أندرويد ضعيف إن توفر.
- البديل المسموح (يُوسم بوضوح): محاكاة Chrome DevTools — CPU throttling 6× + شبكة مقيّدة.
- سجّل كل قياس: الجهاز/المحاكاة، إصدار أندرويد، المتصفح/WebView.

المخرج: ملف واحد في:
takka-main/البحث/04-تقني/R-W01 - قياس Canvas.md

معايير القبول:
- أرقام من جهاز فعلي أو محاكاة موسومة بوضوح، لا تخمين.
- جدول: عدد العناصر / fps / الذاكرة / الحرارة التقديرية.
- عتبة عدد العناصر الآمنة الموصى بها.
- خلاصة: «يبقى 2.5D» أو «نحتاج بديلاً»، مع السبب.

قواعد ملزمة (بروتوكول البحث):
1) سلّم المصادر: أساسي = مراجعة منهجية/تجربة/تقرير رسمي — يُبنى عليه القرار. مساند = دراسة/تقرير — يدعم. سياقي = مقال/مدونة — لا يُستند إليه وحده.
2) وسم كل ادعاء جوهري: [دليل قوي] / [متوسط] / [محدود] / [غير مباشر] / [فرضية تصميم].
3) الاقتباس: العنوان الأصلي — الجهة، السنة — النوع — الرابط — تاريخ الاطلاع — ما يدعمه — حدوده.
4) ممنوع: اختلاق رقم أو رابط؛ ترجمة عنوان كأنه نتيجة؛ توصية بلا «ماذا يعني لتكة».
5) بنية الملف: سؤال المهمة، ما وجدناه بقوة الدليل، ما لا نعرفه، ما ينطبق على تكة، أثر مباشر، أسئلة ≤5، مصادر + سجل بحث.
6) اختم بجدول: التوصية / الأثر على تكة / الكلفة / الثقة / القرار المطلوب.

سقف زمني: 4 ساعات. عند بلوغه سلّم ما وصلت إليه.

يخدم القرار: استمرار 2.5D أم لا (ملف 10 §8.5).

عند الانتهاء أرسل: ملخصاً في 10 أسطر + مسار الملف + أهم 3 نتائج + أهم سؤالين للمالك.
```

```text
أنت وكيل قياس/هندسة في مشروع «تكة» — تطبيق تعليمي ترفيهي عربي أوفلاين أولاً لأطفال غزة.

المهمة: W0-2 — خط الأساس لحجم حزمة التطبيق (Vite + React + Capacitor).

الهدف:
رقم حقيقي لحجم APK الفارغ + React + Vite + Capacitor، لنعرف كم يتبقى من سقف 25MB للمحتوى.

أسئلة البحث:
1. حجم حزمة JS الأساسية بعد vite build (gzip)؟
2. حجم APK الناتج عن Capacitor فارغاً؟
3. كم يتبقى فعلياً من 25MB للمحتوى والصوت والرسوم؟

الطريقة:
- ابنِ مشروع Vite + React + TypeScript + Capacitor فارغاً (لا ميزات).
- نفّذ vite build وسجّل حجم كل قطعة (chunk).
- نفّذ capacitor build/android وسجّل حجم APK.
- سجّل الأوامر المستخدمة حرفياً في الملف.

المخرج: ملف واحد في:
takka-main/البحث/04-تقني/R-W02 - خط أساس الحجم.md

معايير القبول:
- تفكيك حجم بالكيلوبايت لكل اعتماد (react، react-dom، zustand، الخ).
- أرقام فعلية من vite build + APK، مع الأوامر.
- استنتاج: «يتبقى X MB للمحتوى» بحسب سقف 25MB.

قواعد ملزمة (بروتوكول البحث):

سقف زمني: 3 ساعات.

يخدم القرار: سقف الحجم (ملف 10 §13.2) — حزمة لكل صف أم 45MB.
```

## 5. نصائح التشغيل

| النصيحة | التفصيل |
| :--- | :--- |
| **وكيل واحد = مهمة واحدة** | لا ترسل مهمتين لوكيل واحد؛ يفقد العمق ويخلط المخرجات. |
| **ابدأ بـ W0** | المهام الخمس الفورية بالتوازي، ثم راجع قبل أي بناء. |
| **الموجات** | W1 (تربوي) ثم W2 (عربية) ثم W3 (تقني) ثم W4 (سياق/قانون). داخل الموجة: بالتوازي. |
| **التركيب أخيراً** | S1–S5 لا تبدأ قبل إغلاق الموجات؛ هي التي تحوّل البحث إلى قرارات. |
| **لا تُعدّل البرومبت** | إذا بدا البرومبت ناقصاً، أضف سطراً في الملف 12، لا في البرومبت نفسه. |
| **افحص بالبوابة** | استخدم بوابة الجودة في ملف 12 §6 لكل مخرج. |
| **سجل التنفيذ** | حدّث §11 في ملف 12 بعد كل مهمة. |
