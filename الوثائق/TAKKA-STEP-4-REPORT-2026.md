## 3. الخطوة 4 — مخزن مواضع المباني

### 3.1 الفصل المعماري

```
PlacementStore (خام)  ←  Dexie | الذاكرة
        ↓
sanitizePlacement()   ←  دالة نقية: تحقق + fallback
        ↓
PlacementLoadResult { state, source: 'stored' | 'fallback', errors }
```

المخزن يقرأ ويكتب قيمة **خام** (`unknown`)، والتنقية دالة نقية مستقلة. الفائدة: يمكن اختبار بيانات فاسدة فعلياً بكتابتها في المخزن، بدل تزييف حالة داخلية.

### 3.2 قواعد الرفض

| الحالة | النتيجة |
|---|---|
| لا صف محفوظ (أول تشغيل) | التوزيع الافتراضي · `source: 'fallback'` · **بلا تحذير** |
| بنية غير صالحة | `INVALID_PLACEMENT` + التوزيع الافتراضي |
| مبانٍ ناقصة أو مكررة | `INCOMPLETE_PLACEMENT` |
| تصادم موضع | `POSITION_COLLISION:(x,y)` |
| خارج حدود الأرض | `OUT_OF_BOUNDS:id:(x,y)` |
| فشل التخزين نفسه | `STORAGE_UNAVAILABLE` — لا انهيار واجهة |

**قاعدة صارمة:** أي خلل ← استبدال الحالة **كاملاً** بالتوزيع الافتراضي. لا ترقيع جزئي ولا قصّ صامت للإحداثيات، لأن القصّ يخلق تصادماً لم يرتكبه الطفل.

### 3.3 الحفظ

`savePlacement` ينقّي **قبل** الكتابة، ويرفض الكتابة إن كانت الحالة غير صالحة (`ok: false` مع الأسباب). الحفظ مرتين لنفس الملف يبقى صفاً واحداً — المفتاح `profileId` أساسي في Dexie.

### 3.4 ترحيل قاعدة البيانات

```ts
this.version(1).stores({ profiles, evidence, sessions, reports });
this.version(2).stores({ ...same, placements: 'profileId, updatedAt' });
```

إضافة جدول فقط — لا تغيير على أي جدول قائم، فلا خطر على بيانات الإتقان. وأُضيف حذف صف المواضع إلى `deleteProfile` حتى لا يبقى أثر لملف محذوف.

### 3.5 الاختبارات الستة

| # | الاختبار |
|---|---|
| 1 | حفظ/قراءة كاملة تعيد نفس المواضع بمصدر `stored` |
| 2 | ملف بلا مواضع ← التوزيع الافتراضي بهدوء |
| 3 | بنية فاسدة (`x: 'خمسة'`) ← `INVALID_PLACEMENT` بلا رمي |
| 4 | مبنى مكرر + تصادم ← الخطآن معاً ثم fallback |
| 5 | `(0,0)` مرفوض على أرض 10 ومقبول على 12 |
| 6 | صف واحد فقط، والحفظ الفاسد لا يطمس السليم |
